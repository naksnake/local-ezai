# WebUI Admin Center — Architecture

**What it is:** the platform's management console — the WebUI counterpart
of the `local-ezai` CLI. **What it grows from:** the existing monitor
service (:8888, RBAC admin/viewer, Knowledge Base bar, health view) — an
evolution of a component we already own, not a new frontend project and
not an OpenWebUI fork.

## 1. Position in the architecture

```
OpenWebUI :3000 ──deep links──►  Admin Center :8888  ──REST──► ezaid :8010
 (chat, tools)                   (monitor service,              (Platform
                                  extended)                      Control Plane)
local-ezai CLI ────────────────────────────────────────REST──►──────┘
```

- The Admin Center renders **only** what the Control Plane serves; it owns
  no business logic and no direct file/docker access. Anything the Admin
  Center can do, the CLI can do — same API, same audit trail
  ([CLI_AND_WEBUI_STRATEGY.md](CLI_AND_WEBUI_STRATEGY.md)).
- Existing monitor duties (service health, KB ingest, benchmarks) remain
  as the **Health** and **Knowledge** sections — nothing is removed.

## 2. Information architecture (pages)

| Page | Content | Mutations offered (all via control plane) |
|---|---|---|
| **Overview** | stack health (8 services + ezaid), active engine/provider, active model set per group, pending-approval count, last runs | — |
| **Models** | catalog (installed/available), per-model: provider, group, quant, size, state, benchmark history; routing table (role → primary/fallback, resolved exactly like `local-ezai models`) | install · activate (→ approval) · benchmark · upgrade (→ approval) · rollback · retire |
| **Routing** | role → group → model resolution graph; per-role "explain" narrative; generation history diff view | edit role/group assignment (→ new generation, approval when it changes a serving role) |
| **Runs** | run list (swe/sprint/evolve), filters; run detail: plan, validation incl. Browser QA, review verdict + findings, healing iterations, models used, journal viewer, exec-audit viewer, branch info | cancel run |
| **Governance** | the approval queue: model activations/upgrades, evolution PRs (proposal, benchmark before/after, diffstat, PR/bundle link), release candidates | approve · reject (with reason) — **admin role only** |
| **Sprints** | sprint reports incl. dependency graphs (mermaid already generated by the runtime) | — |
| **Memory** | per-project memory browser (rules/styles/decisions/fixes), lessons_learned view | add curated rule/style (same as `memory --add`) |
| **Projects** | repos registered for chat-ops/WebUI-triggered work | add/remove project (admin) |
| **Health** | existing monitor health + tokens/sec bench + exec-audit tail + disk usage of runs/workspaces | prune old runs/workspaces |
| **Knowledge** | existing KB bar (unchanged) | ingest (unchanged) |

## 3. The Governance queue (the page that matters most)

One queue, three item types, one contract: **agents propose, humans
approve** (CLAUDE.md).

| Item type | Created by | Evidence shown | Approve action |
|---|---|---|---|
| **Model activation/upgrade** | `model activate/upgrade` request (CLI or Admin Center) | benchmark deltas (probe + quality metrics + tokens/sec), affected roles, generation diff | control plane renders new generation → reloads LiteLLM/engine ([MODEL_LIFECYCLE_MANAGEMENT.md](MODEL_LIFECYCLE_MANAGEMENT.md)) |
| **Evolution PR** | `evolve` pipeline | proposal, benchmark before/after, review verdict, PR/bundle link | marks approved + deep-links to the forge PR (merge itself stays on the forge — the platform still never merges) |
| **Release candidate** | release procedure | test/lint status, RELEASE_NOTES diff | records sign-off (MAINTENANCE_GUIDE §5) |

Every decision writes an immutable audit record (who, when, what,
evidence snapshot) to the control plane's governance log.

## 4. AuthN/AuthZ

- Reuses the monitor's existing RBAC: `admin` (mutations + governance) and
  `viewer` (read-only), HTTP Basic today.
- V1 adds an optional **trusted-header SSO handoff from OpenWebUI**
  (OpenWebUI admin ⇒ Admin Center admin) so the "front door" feels like
  one product; Basic auth remains the fallback. No new identity system in
  V1.
- The Admin Center authenticates to `ezaid` with its service token;
  user identity is forwarded per request for the audit trail.

## 5. UX principles

1. **Evidence next to every button** — an approve button never appears
   without the benchmark/diff/report that justifies it.
2. **Deep-linkable everything** — `/runs/<id>`, `/models/<name>`,
   `/governance/<item>`; chat and CLI print these URLs.
3. **No hidden state** — every page footer names the generation / registry
   file the view was rendered from.
4. **Parity or absence** — a mutation exists here only if the CLI verb
   exists ([CLI_AND_WEBUI_STRATEGY.md](CLI_AND_WEBUI_STRATEGY.md) §3).
5. Existing monitor look-and-feel evolves; no framework rewrite.

## 6. Explicit non-goals

Editing raw YAML in the browser (state is mutated through typed operations
only) · a code editor / IDE · merging PRs (that stays on the forge) ·
user management beyond the two RBAC roles (V1.x).
